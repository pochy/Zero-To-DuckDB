# Part 1: DuckDB入門

## このPartでできるようになること

DuckDB CLIでSQLを実行し、テーブルを作り、CSVを直接読み、簡単な集計ができるようになります。

このPartで大事なのは、SQLの文法をたくさん覚えることではありません。DuckDBの最初の強みである「DBサーバーを用意せず、ファイルやローカルDBに対してすぐSQLを実行できる」感覚をつかむことです。

Part 0ではDuckDBを分析向けSQLエンジンとして位置づけました。Part 1では、その位置づけを手で確認します。

## このPartの設計思想

Part 1の目的は、CLI操作を覚えることではありません。DuckDBが「手元で観察しながらSQLを育てる」ための道具であることを体験することです。

実務のデータ処理では、最初から完成したSQLを書くことはほとんどありません。まず少し読む、件数を見る、型を見る、想定と違う行を見る、そしてSQLを修正する。この観察と修正の反復が必要です。DuckDB CLIは、この反復を非常に短い距離で行えます。

## なぜこの考え方が必要なのか

SQLの初心者は、構文を正しく書くことをゴールにしがちです。しかしデータ処理では、構文が正しくても意味が間違っていることがよくあります。列名を取り違えた、DBファイルを間違えた、型推論が想定と違った、NULLを見落とした、という失敗は文法エラーではありません。

だからこそ、Part 1では `.tables`、`.schema`、`count(*)`、`LIMIT` のような観察の道具を重視します。これらは補助コマンドではなく、データを信頼してよいか確かめるための基本姿勢です。

## 初心者が誤解しやすいこと

初心者は、CSVを読めた瞬間に「取り込み完了」と考えがちです。しかし、読めることと、後続処理が信頼してよいことは違います。

また、DBファイルを作ることを永続化の完成だと考えることもあります。実務では、DBファイルそのものよりも、DBファイルを再生成できるSQLと手順が重要です。このチュートリアルで `product_pipeline.duckdb` をGit管理しないのは、生成物ではなく生成方法を正本にするためです。

## プロはどう判断するか

プロは、CLIで試したSQLをそのまま本番手順にしません。CLIで観察し、安定したらSQLファイルへ移し、Makefileから実行し、テストで期待値を固定します。

Part 1の小さな `products` テーブルは、おもちゃではありません。あとでraw/staging/mart、品質チェック、Parquet出力へ広げるための最小モデルです。小さな例で「観察してから信頼する」姿勢を身につけることが、このPartの本質です。

## 背景にある設計原則

CLIを学ぶ理由は、コマンド操作に慣れるためだけではありません。CLIは、データに対して仮説を立て、すぐ確認し、間違いを修正するための最短経路です。実務データでは、最初の想定が外れることが普通です。列名が違う、件数が違う、型が違う、NULLが混ざっている。そのずれを早く見つけるために、CLIで小さく観察します。

ただし、CLIは最終的な保管場所ではありません。CLIは探索の場、SQLファイルは処理の正本、Makefileは実行順の契約、テストは期待値の固定です。この役割を分けることで、試行錯誤と運用を混ぜずに済みます。

このPartでは、最初のSQLを動かすことよりも、「動いた後に何を見るか」を重視します。結果が出たら件数を見る。スキーマを見る。数行を見る。期待と違う行を見る。SQLは、書くものではなく、観察しながら育てるものです。

## まず知るべき言葉

- CLI: ターミナルから使うコマンド
- database file: `.duckdb` 拡張子などで保存するDuckDBのDBファイル
- in-memory DB: ファイルに保存せず、その場限りで動くDB
- table: 行と列を持つ永続的なデータ
- view: SQLを名前付きで保存した仮想的な表
- replacement scan: ファイル名やDataFrameをSQLのFROMに置ける仕組み
- meta command: `.tables` や `.schema` のようにCLIで使う補助コマンド

## DuckDB CLIで何を学ぶのか

DuckDBはPythonやNode.jsからも使えますが、最初はCLIで学ぶのがよいです。CLIは、DuckDBエンジンの動きを最短距離で観察できるからです。

CLIでできることは、実務のバッチやNotebookでもほぼ同じ考え方で使います。

- SQLを1つずつ試す
- テーブルの中身を確認する
- ファイルを直接読む
- SQLファイルを実行する
- DBファイルに結果を残す
- `.tables` や `.schema` で状態を確認する

このPartで作る小さな `products` テーブルは、最終課題の商品情報統合パイプラインの縮小版です。最初は3件の商品だけを扱いますが、考えることは同じです。

## 手順1: CLIでDBファイルを開く

まず、DBファイルを指定してDuckDBを起動します。

```bash
duckdb intro.duckdb
```

このコマンドは、DuckDBサーバーへ接続しているわけではありません。`duckdb` CLIプロセスの中でDuckDBエンジンが動き、`intro.duckdb` というローカルファイルに状態を保存します。

プロンプトが出たらSQLを実行します。

```sql
SELECT 'hello duckdb' AS message;
```

期待する出力は `message` 列に `hello duckdb` が表示されることです。

ここで見るべき点は3つあります。

1. SQLを実行するためにDBサーバーを起動していない
2. `SELECT` の結果が表として表示される
3. ファイル名を指定しているので、作ったテーブルはCLIを閉じても残る

もし次のようにファイル名なしで起動した場合は、その場限りのDBとして使います。

```bash
duckdb
```

ちょっとした確認には便利ですが、作ったテーブルを後で使いたい場合は `intro.duckdb` のようにファイル名を指定します。

## 手順2: テーブルを作る

次に、商品テーブルを作ります。

```sql
CREATE TABLE products (
  product_id VARCHAR,
  product_name VARCHAR,
  price INTEGER,
  category VARCHAR
);
```

ここでは、4つの列を定義しています。

| 列 | 型 | 意味 |
| --- | --- | --- |
| `product_id` | `VARCHAR` | 商品ID |
| `product_name` | `VARCHAR` | 商品名 |
| `price` | `INTEGER` | 価格 |
| `category` | `VARCHAR` | カテゴリ |

`VARCHAR` は文字列、`INTEGER` は整数です。実務データでは、最初からこのようにきれいな型で来るとは限りません。むしろ、価格が文字列だったり、カテゴリが表記ゆれしていたりします。

このPartではまず整ったテーブルを作り、Part 2とPart 3で汚い入力をどう扱うかに進みます。

データを入れます。

```sql
INSERT INTO products VALUES
  ('p001', 'Coffee Beans', 1200, 'food'),
  ('p002', 'Tea Bag', 800, 'food'),
  ('p003', 'Mug Cup', 1500, 'kitchen');
```

中身を確認します。

```sql
SELECT * FROM products;
```

期待する出力は3行です。ここでは、DBに何が保存されたかを確認する習慣をつけます。SQLは「書いたら終わり」ではなく、「出力を見て、意図した状態になっているか確認する」ものです。

## 手順3: 集計する

カテゴリごとに件数と平均価格を集計します。

```sql
SELECT
  category,
  count(*) AS product_count,
  avg(price) AS avg_price
FROM products
GROUP BY category
ORDER BY category;
```

このSQLには、分析SQLの基本が入っています。

| 句 | 役割 |
| --- | --- |
| `SELECT` | 出したい列や計算結果を決める |
| `FROM` | どの表から読むかを決める |
| `GROUP BY` | どの単位で集計するかを決める |
| `ORDER BY` | 結果の並び順を決める |

`GROUP BY category` は、「1商品ずつ見る」のではなく「カテゴリ単位で見る」という意味です。分析では、この粒度の切り替えが重要です。

観察ポイントは次の通りです。

- `food` は2件になる
- `kitchen` は1件になる
- `avg_price` はカテゴリ内の価格平均になる

このような小さな集計が、後の品質チェックやカテゴリ別商品数の土台になります。

## 手順4: メタコマンドを使う

DuckDB CLIでは、SQL以外にドットで始まるコマンドがあります。

```sql
.tables
.schema products
.mode markdown
.mode duckbox
.mode line
.headers on
```

`.tables` はテーブル一覧、`.schema products` は `products` テーブルの定義確認に使います。

`.mode` は表示形式を切り替えます。`markdown` は教材やメモへ貼りやすく、`duckbox` はCLI上で表として読みやすく、`line` は列数が多い1行を縦に確認したい時に便利です。

分析中は「今どんな表があるか」「列名は何か」「型は何か」を何度も確認します。初心者はSQLエラーが出ると文法だけを疑いがちですが、実際には列名の勘違い、テーブル名の勘違い、型の勘違いがよくあります。

`.schema` を見る習慣があると、次のような問題に早く気づけます。

- `price` が数値ではなく文字列になっている
- `category_name` だと思っていた列が `category` だった
- テーブルを作ったつもりが、別のDBファイルを開いていた

## 手順5: CSVを直接読む

DuckDBらしさが出るのは、ファイルを直接読めるところです。既存のサンプルCSVを読みます。

```bash
cd product-data-duckdb
duckdb
```

```sql
SELECT *
FROM read_csv('data/incoming/maker_a/products.csv', header = true)
LIMIT 5;
```

ここでは、事前に `CREATE TABLE` していません。DuckDBがCSVを読み、SQLの結果として表示しています。

この使い方は、実務の初期調査に向いています。

- ファイルの列名を確認する
- 先頭数行を見る
- 価格や日付がどんな文字列で入っているか見る
- 想定外の空欄や表記ゆれを見つける

重要なのは、直接読みは「調査」に向いているということです。何度も使う変換や品質チェックを作る段階では、rawテーブルへ保存して、処理を再現可能にします。

## 手順6: CSVをテーブル化する

CSVをrawテーブルとして保存します。

```sql
CREATE OR REPLACE TABLE raw_products AS
SELECT *
FROM read_csv('data/incoming/maker_a/products.csv', header = true, all_varchar = true);

SELECT count(*) AS rows FROM raw_products;
```

`CREATE OR REPLACE TABLE ... AS SELECT` は、SELECT結果からテーブルを作る書き方です。ファイルを毎回直接読むのではなく、一度DuckDB内に取り込みたい場合に使います。

ここで重要なのは `all_varchar = true` です。これは、CSVの列をすべて文字列として読む設定です。

一見すると、価格は最初から数値にした方が正しそうです。しかし、実務のCSVでは次のような値が混ざります。

```text
1200
1,200
1200円
N/A
未定
空欄
```

最初の読み込みで数値化を強制すると、どこかの行で処理が止まったり、ファイルごとに型推論が変わったりします。raw層では、まず入力を落とさず受けることを優先します。数値化はPart 3のstaging層で `try_cast` を使って行います。

## 直接読む、テーブル化する、VIEWにする

DuckDBでは、同じCSVに対していくつかの扱い方があります。

| 方法 | 使う場面 |
| --- | --- |
| 直接 `read_csv` する | その場で中身を確認したい |
| テーブル化する | 後続処理で何度も使う、状態を固定したい |
| VIEWにする | SQL定義だけ保存し、実データは都度読む |

初心者は何でもテーブル化しがちですが、常にそれが最適とは限りません。小さな調査なら直接読むだけで十分です。再現可能なパイプラインにするなら、rawテーブルとして受けた方が後続の品質チェックを安定させやすくなります。

このチュートリアルの完成実装では、`sql/02_load_raw.sql` で入力ファイルをrawテーブルに読み込みます。これは、後の正規化、品質チェック、Parquet出力を同じ入力状態から再実行できるようにするためです。

## 最初の小さな例と実務パイプラインのつながり

Part 1の `products` テーブルは小さすぎて、実務と関係が薄く見えるかもしれません。しかし、この小さな例には、後のパイプラインで何度も出てくる考え方が含まれています。

```sql
CREATE TABLE products (
  product_id VARCHAR,
  product_name VARCHAR,
  price INTEGER,
  category VARCHAR
);
```

この定義を見たとき、プロは次のような問いを考えます。

- `product_id` は本当に一意か
- JANコードのような外部識別子とは別物か
- `price` は税込か税抜か
- 通貨は固定か
- `category` は自由入力かマスタ参照か
- 商品名が空の場合は許すのか
- 同じ商品が複数カテゴリに属することはあるか

初心者向けの最初のSQLでは、これらをすべて設計しません。最初から複雑にすると手が止まるからです。しかし、実務では必ず出てくる問いです。

このチュートリアルでは、Part 1で最小の表を作り、Part 2でファイル取り込み、Part 3で正規化、Part 4以降で分析・運用へ広げます。つまり、最初の小さな表は、後で壊れる前提で作る練習台です。

## CLI操作で身につけるべき観察習慣

DuckDB CLIでは、SQLを書けること以上に、観察する習慣が重要です。

良い作業の流れ:

```text
SQLを書く
  ↓
少ない行で確認する
  ↓
件数を見る
  ↓
スキーマを見る
  ↓
想定と違う行を探す
  ↓
SQLを修正する
```

悪い作業の流れ:

```text
SQLを書く
  ↓
何となく結果が出たので次へ進む
```

DuckDBはファイルを直接読めるため、結果がすぐ出ます。その速さは強みですが、結果を確認せずに進むと、間違いも速く広がります。

Part 1の段階で、次のSQLを習慣にします。

```sql
SELECT count(*) FROM raw_products;
SELECT * FROM raw_products LIMIT 5;
.schema raw_products
```

件数、サンプル、スキーマを見るだけで、多くのミスを早期に発見できます。

## 永続化をどう考えるか

DuckDBでは、ファイル名を指定しない一時DBと、`.duckdb` ファイルに保存するDBがあります。

一時DBが向いている場面:

- その場限りのSQL確認
- 小さな計算
- サンプルデータの試し読み
- Notebook内の一時的な検証

DBファイルが向いている場面:

- 複数SQLファイルを順番に実行する
- raw/staging/martを保持する
- テストを実行する
- 別プロセスから結果を読む
- 後で同じ状態を再確認する

このチュートリアルの完成実装では、`product_pipeline.duckdb` を使います。これは、パイプラインの途中状態をDuckDBファイルに保持し、品質チェックやテストから参照できるようにするためです。

ただし、DuckDBファイルをGitに入れるわけではありません。DBファイルは生成物です。Gitに入れるのは、DBファイルを作るSQLとスクリプトです。

## SQLを書く時の粒度感

Part 1では小さなSQLを直接CLIに入力します。これは学習には向いていますが、実務ではSQLが長くなります。

実務では、次のように段階を分けます。

```text
CLIで試す
  ↓
うまくいったSQLをファイルに移す
  ↓
Makefileから実行する
  ↓
テストで期待値を固定する
```

最初から完璧なSQLファイルを書く必要はありません。CLIで観察しながら作り、安定したらSQLファイルへ移します。

逆に、いつまでもCLI履歴やNotebookセルだけに処理を置いておくと、誰がどう再実行するのか分からなくなります。Part 1でCLIを学ぶのは、最終的にCLIに閉じるためではなく、SQLを安全に育てるためです。

## よくある設計ミス

最初の段階でよくある設計ミスを整理します。

| ミス | なぜ問題か | より良い考え方 |
| --- | --- | --- |
| CSVをすぐ最終テーブルに入れる | 不正値の原因を追いにくい | rawとして受けてからstagingで整える |
| 型推論を全面的に信じる | ファイル追加で型が変わる | rawでは文字列、stagingで型を決める |
| `SELECT *` を本番SQLに残す | 列追加に弱い | 出力列を明示する |
| DBファイルをGitに入れる | 差分が読めない | SQLと入力をGit管理する |
| 件数確認をしない | 欠損や重複に気づかない | `count(*)` とサンプル確認を挟む |

これらは小さなミスに見えますが、データパイプラインでは後工程の信頼性に直結します。

## よくあるつまずき

CLIを閉じるとインメモリDBの内容は消えます。ファイル名を指定して `duckdb intro.duckdb` のように開くと、DBファイルに保存されます。

CSVの型推論に任せると、後で別ファイルを読んだときに型が合わないことがあります。実務ではraw層を文字列で受け、staging層で型を決める方が調査しやすくなります。

`.tables` で期待したテーブルが見えない場合は、別のDBファイルを開いている可能性があります。今どのディレクトリで `duckdb` を起動したか、ファイル名を指定したかを確認してください。

`SELECT *` は調査には便利ですが、パイプラインの最終SQLでは列を明示する方が安全です。入力ファイルに列が追加されたとき、意図しない列まで後続処理に流れることを防げます。
