# Part 0: DuckDBの全体像を理解する

## このPartでできるようになること

DuckDBが何者で、どこで使うべきで、どこで使うべきではないかを判断できるようになります。

このPartのゴールは、DuckDBを「SQLが使える小さなDB」と曖昧に覚えることではありません。次の一文を、自分の言葉で説明できる状態を目指します。

> DuckDBは、アプリや分析環境の中に直接組み込める、分析処理向けの軽量SQLエンジン。

特に重要なのは、DuckDBをWebアプリのメインDBとして学ばないことです。DuckDBは、分析、前処理、ファイル処理、品質チェック、Parquet変換、ローカル検証に強い道具です。一方で、ログイン、注文登録、決済、在庫更新のような多人数・同時更新の中心に置くDBではありません。

## このPartの設計思想

DuckDBを理解するうえで最初に必要なのは、機能一覧ではなく「配置」の感覚です。DuckDBは、PostgreSQL、BigQuery、pandas、Polarsの代わりに何でも担当する道具ではありません。むしろ、既存のDB、ファイル、Notebook、アプリの間に入り、データを観察し、検証し、変換し、説明可能な成果物にするための道具です。

このPartでは、DuckDBを「小さなDB」としてではなく、「データの責務を分けるための分析エンジン」として見ます。正本データを管理する場所、汚い入力を受ける場所、品質を判定する場所、後続へ渡す場所を混ぜないことが、実務でDuckDBを安全に使うための基本です。

## なぜこの考え方が必要なのか

DuckDBは導入が簡単です。サーバーを立てず、ファイルを直接読み、SQLですぐ結果を出せます。この簡単さは強みですが、同時に誤用の入口にもなります。

「SQLが使えるならWebアプリのDBにもできる」「PostgreSQLを置き換えられる」「pandasより速いなら全部DuckDBでよい」と考えると、責務が崩れます。実務では、できることと任せるべきことを分けなければなりません。

DuckDBの哲学は、正本を奪うことではなく、正本やファイルから安全に読み、後続が使える形に整えることです。だからこそ、このチュートリアルでは最初からOLTP/OLAP、embedded、ファイル処理、品質チェックという背景を重視します。

## 初心者が誤解しやすいこと

初心者はDuckDBを「SQLiteの速い版」または「PostgreSQLの軽い版」と捉えがちです。この理解は半分だけ正しいです。軽量で組み込みやすい点は似ていますが、DuckDBの中心は分析です。

もう1つの誤解は、DuckDBを使うこと自体が設計である、という考えです。実際には、DuckDBをどこに置くかが設計です。入力ファイルと正本DBの間に置くのか、Notebookの前処理として置くのか、アプリのリクエスト処理の中に置くのかで、リスクも価値も変わります。

## プロはどう判断するか

プロは、まずデータの責務を見ます。このデータは正本なのか、入力候補なのか、検証結果なのか、配布用成果物なのか。その分類が先です。

DuckDBに向いているのは、入力候補、検証結果、分析用中間成果物、Parquet出力です。向いていないのは、注文、決済、権限、ユーザー状態のような正本OLTPデータです。この線を引けることが、DuckDBを実務で使う第一歩です。

## 背景にある設計原則

DuckDBの背景にある設計原則は、分析処理をアプリケーションDBから切り離すことです。アプリケーションDBは、正しい現在状態を安全に更新するための場所です。一方、分析や前処理では、過去のファイル、壊れた値、途中の変換、品質エラーを観察する必要があります。この2つを同じ場所に押し込むと、正本DBに汚れた入力や一時的な検証処理が入り込みます。

DuckDBは、正本DBの外側に分析用の作業机を作る道具です。作業机なので、試行錯誤できます。ファイルを直接読めます。Parquetへ出せます。ただし、作業机を会社の台帳にしてはいけません。ここを間違えると、DuckDBの便利さがそのまま設計リスクになります。

このPartで重要なのは、DuckDBを「採用するかどうか」ではなく、「どこに置くか」です。既存DBを置き換えるのではなく、既存DBやファイルから安全に読み、分析・検証・変換した成果物を後続へ渡す。この配置を理解すると、以降の章で出てくるraw/staging/mart、品質チェック、Parquet、JSON契約の意味がつながります。

## まず知るべき言葉

- OLTP: 小さな読み書きを安全に処理する用途
- OLAP: 大量データを読み、集計・分析する用途
- embedded DB: アプリやCLIのプロセス内で動くDB
- in-process: 別サーバーではなく、同じプロセス内で実行されること
- columnar execution: 列単位で処理する分析向けの実行方式
- Parquet: 分析向けの列指向ファイル形式
- DataFrame: pandasやPolarsのように、表データをプログラム上で扱う構造

## DuckDBとは何か

DuckDBは、分析処理向けのSQLエンジンです。CLI、Python、Node.js、Rなどの中から直接呼び出せます。PostgreSQLやMySQLのように常駐サーバーを立て、アプリがネットワーク越しに接続する形とは違います。

たとえば、次のような場面でDuckDBは自然に使えます。

- 複数メーカーから届いたCSVをまとめて確認する
- Excel、JSON Lines、ParquetをSQLで横断して読む
- PostgreSQLから読み出したデータをローカルで検証する
- 不正な価格、欠損JANコード、未知カテゴリを品質チェックする
- 正常化したデータをParquetに変換して分析基盤へ渡す
- Notebookの前処理をSQLとして再現可能にする

逆に、次のような場面ではDuckDBを中心に置くべきではありません。

- ユーザー登録やログイン状態を管理する
- ECサイトの注文をリアルタイムに登録する
- 多数のアプリケーションサーバーから同時に更新する
- 複雑な権限管理、監査、バックアップ運用をDBサーバーに任せる
- 中央の業務DBとして何年も継続運用する

初心者がつまずくのは、DuckDBが「SQLを話す」ために、PostgreSQLやSQLiteと同じ用途だと考えてしまう点です。SQLは共通の言語ですが、道具としての役割は違います。

## OLTPとOLAP

DBの使い分けでは、まずOLTPとOLAPを分けて考えます。

OLTPは、Online Transaction Processingの略です。注文登録、在庫更新、ユーザー情報変更のように、小さな更新を大量に、安全に、同時に処理します。重要なのは、1件ごとの正確性、トランザクション、同時接続、制約、ロック、復旧です。

OLAPは、Online Analytical Processingの略です。売上集計、商品マスタ検証、ログ分析、ファイル変換、ダッシュボード用集計のように、多くの行を読み、必要な列を選び、集計します。重要なのは、列の読み取り効率、圧縮、並列処理、ファイル形式、スキャン性能です。

同じ「商品データ」でも、OLTPとOLAPでは見方が変わります。

| 場面 | 向いている考え方 | 例 |
| --- | --- | --- |
| 商品を1件登録する | OLTP | 管理画面から商品マスタへINSERTする |
| 商品を10万件検証する | OLAP | CSVを読み、価格不正やカテゴリ不一致を集計する |
| 注文ステータスを更新する | OLTP | `paid` から `shipped` に更新する |
| 月次の売上を集計する | OLAP | 注文明細を読み、カテゴリ別に合計する |

DuckDBはOLAP側の道具です。アプリ本体のDBをDuckDBに置き換えるのではなく、PostgreSQLなどから必要なデータを読み出し、分析・検証・変換する場所に置くと力を発揮します。

## embedded / in-process DBとは何か

DuckDBは、サーバーとして別プロセスで待ち受けるDBではありません。次のように実行すると、DuckDBのエンジンがCLIプロセス内で動きます。

```bash
duckdb my_analysis.duckdb
```

Pythonから使う場合も、同じ考え方です。Pythonプロセス内にDuckDBエンジンが組み込まれ、SQLを実行します。

この性質には、大きな利点があります。

- ローカルPCだけで始められる
- DockerやDBサーバーなしでも分析できる
- NotebookやCLIバッチに組み込みやすい
- テストで一時DBを作りやすい
- ファイル変換ツールとして配布しやすい

一方で、弱点もあります。

- 多数のアプリから同時に更新する中心DBにはしにくい
- DBサーバーにあるような接続管理や権限管理を期待しにくい
- チーム全体の共有DWHとしては別の運用設計が必要になる

つまり、DuckDBの「軽さ」は、サーバー運用を省ける強みであると同時に、サーバーDBとしての役割を期待しすぎてはいけないという制約でもあります。

## なぜ「SQLite for Analytics」と呼ばれるのか

DuckDBはしばしば「SQLite for Analytics」と呼ばれます。この表現には、半分正しく、半分注意が必要です。

SQLiteとDuckDBは、どちらも軽量で、ローカルファイルとしてDBを扱え、アプリに組み込みやすいという共通点があります。`sqlite.db` のように単一ファイルで扱える体験と、`analysis.duckdb` のようにローカルで完結する体験は似ています。

しかし、得意分野は違います。

SQLiteは、小さなアプリの状態管理やローカルOLTPに向いています。行単位の読み書き、シンプルな永続化、アプリ組み込みの業務データ管理が主戦場です。

DuckDBは、大量の行を読み、列を選び、集計し、ファイルを横断する分析処理に向いています。CSV、JSON、Parquetを直接読み、DataFrameや外部DBともつながります。

そのため「SQLiteと同じように軽く使えるが、用途は分析」という意味で「SQLite for Analytics」と捉えるのが安全です。「SQLiteの完全な置き換え」ではありません。

## 他の道具との違い

DuckDBは万能ではありません。実務では、既存の道具と組み合わせます。

| 道具 | 得意なこと | DuckDBとの関係 |
| --- | --- | --- |
| SQLite | 軽量なアプリ内DB、ローカル状態管理 | DuckDBはより分析・ファイル処理寄り |
| PostgreSQL | WebアプリのメインDB、堅牢なトランザクション | DuckDBはPostgreSQLから読み出して分析する側 |
| BigQuery / Snowflake | 大規模DWH、チーム共有、権限管理 | DuckDBはローカル検証や小中規模処理に向く |
| ClickHouse | 高速な分析DBサーバー、継続的な集計基盤 | DuckDBはサーバー運用なしで始める分析エンジン |
| pandas | Python上の表データ処理 | DuckDBはSQLでファイルやDBを横断しやすい |
| Polars | 高速なDataFrame処理 | DuckDBはSQL、外部ソース、Parquet連携が自然 |

判断の軸は「どの言語が好きか」ではありません。次のように考えます。

- アプリの正規データを管理するなら PostgreSQL
- ローカルアプリに小さく永続化するなら SQLite
- SQLで複数ファイルを横断して前処理するなら DuckDB
- Pythonで細かいアルゴリズム処理をするなら pandas / Polars
- チーム共有の大規模DWHを運用するなら BigQuery / Snowflake / ClickHouse

このチュートリアルでは、DuckDBを「既存DBやファイルの間に入り、分析可能な形に整えるエンジン」として扱います。

## DuckDBが得意なこと

DuckDBが特に強いのは、ファイルとSQLの距離が近いことです。

通常、CSVをSQLで扱うには、DBへインポートし、テーブルを作り、型を合わせる必要があります。DuckDBでは、ファイルを直接 `SELECT` できます。

```sql
SELECT *
FROM read_csv('data/incoming/maker_a/products.csv', header = true)
LIMIT 5;
```

この体験は、実務の前処理で非常に便利です。まだ正式なテーブル設計が決まっていなくても、まず中身を見られます。

DuckDBが得意な処理を、このチュートリアルの文脈で整理すると次の通りです。

- CSV、Excel、JSON Lines、ParquetをSQLで読む
- 複数ファイルをまとめて読み、ソースファイル名を保持する
- raw、staging、martのように段階を分けて変換する
- 汚い文字列や価格を `try_cast` で安全に正規化する
- SQLiteやPostgreSQLのマスタを読み、入力データとJOINする
- 品質チェック結果をSQLテーブルとして出す
- 正常化したデータをParquetやpartitioned datasetへ出力する
- NotebookやNode.js CLIに品質チェック結果を渡す

## DuckDBが苦手なこと

DuckDBが苦手なことも、早い段階で明確にしておきます。

まず、多数ユーザーの同時書き込みには向きません。DuckDBは分析処理向けであり、注文登録のような細かい更新が常時発生する中心DBとして設計するものではありません。

次に、Webアプリの権限管理や監査の中心にも向きません。アプリのユーザー、権限、セッション、決済状態のようなデータは、PostgreSQLなどのサーバーDBに置く方が自然です。

また、巨大なDWHの完全な代替でもありません。組織全体でデータを共有し、権限を分け、長期運用し、複数チームが同時に使うなら、BigQuery、Snowflake、ClickHouseなどを検討します。

DuckDBは「小さいから弱い」のではありません。役割が違います。ローカルまたはアプリ内で分析処理を高速に行い、ファイルや外部DBを扱いやすくするための道具です。

## 業務での使いどころ

実務では、DuckDBは次のような位置に置くと使いやすくなります。

```text
メーカーCSV / Excel / JSON
        ↓
      DuckDB
        ↓
品質チェック / 正規化 / Parquet出力
        ↓
分析、BI、ML、アプリ用バッチ
```

この流れでは、DuckDBは「入力データをそのまま信じない」ための場所です。ファイルを読み、出どころを残し、型を整え、マスタと照合し、エラーを分類します。

たとえば商品情報統合では、次のような問題が起きます。

- 価格が `1,200円` や `N/A` のような文字列になっている
- JANコードが空欄になっている
- カテゴリ名が `Food`、`food`、`食品` のように揺れている
- 同じJANコードの商品が複数ファイルに出てくる
- Excelだけ列名やシート名が違う
- AI-OCRのJSONだけネスト構造になっている

DuckDBは、こうした問題をSQLで観察し、分類し、修正方針を明確にするのに向いています。

## 業務シナリオで考えるDuckDBの役割

ここで、少し具体的な業務シナリオで考えます。

小売企業で、毎週月曜日に複数メーカーから商品ファイルが届くとします。メーカーAはCSV、メーカーBもCSVですが列順が違います。メーカーCはExcelで、AI-OCRチームからはJSON Linesが届きます。社内のカテゴリマスタはPostgreSQLにあります。

このとき、初心者は次のように考えがちです。

```text
全部PostgreSQLにINSERTすればよい
または
全部pandasで読み込んで処理すればよい
```

どちらも場合によっては動きます。しかし、実務では問題が出ます。

PostgreSQLに直接入れる場合、汚い入力を正本DBに近づけすぎます。価格が `N/A` の行、カテゴリが未知の行、JANコードが欠けた行を、どの時点で止めるのかを設計しなければなりません。取り込み失敗時にロールバックするのか、一部だけ入れるのか、エラー行をどう返すのかも考える必要があります。

pandasだけで処理する場合、探索は速いですが、SQLとしてレビューしにくくなることがあります。複数ファイル、外部DB、Parquet出力、品質チェック、アプリ連携まで広がると、Notebookのセル順や一時変数に依存しやすくなります。

DuckDBを挟むと、次のような中間地点を作れます。

```text
入力ファイルや外部DB
  ↓
DuckDBでraw取り込み
  ↓
stagingで正規化
  ↓
martで品質チェック
  ↓
正常データだけParquetへ
```

この構成では、DuckDBは正本DBではありません。汚い入力を観察し、分類し、後続へ渡せる形に整える作業エンジンです。この役割が明確だと、DuckDBの強みを活かしつつ、WebアプリDBやDWHとの責務を混ぜずに済みます。

## 初心者の悪いメンタルモデルとプロのメンタルモデル

DuckDBを学ぶとき、最初に直すべきメンタルモデルがあります。

悪いメンタルモデル:

```text
DuckDBは小さいPostgreSQLのようなもの。
SQLが使えるなら、アプリDBにも分析DBにも何にでも使える。
```

より良いメンタルモデル:

```text
DuckDBは、ファイルや外部DBをローカル/組み込み環境でSQL処理する分析エンジン。
正本DBではなく、分析・検証・変換の場所として使う。
```

この違いは、アーキテクチャ判断に直結します。

たとえば「商品管理画面を作りたい」という相談なら、商品マスタの正本はPostgreSQLに置くのが自然です。DuckDBは、メーカーから届いた商品候補ファイルを検証し、PostgreSQLへ取り込む前の品質チェックや、取り込み後の分析に使います。

「CSVを20個受け取って、カテゴリ別に不正価格を確認したい」という相談なら、DuckDBはかなり自然です。サーバーを立てずに、ファイルを直接読み、SQLで集計し、エラー行を出せます。

プロは「この道具でできるか」だけを見ません。「この道具にその責務を持たせると、後で誰が運用できるか」を見ます。

## 判断のための質問リスト

DuckDBを使うべきか迷ったら、次の質問を使います。

| 質問 | DuckDBに向く答え | 別の道具を検討する答え |
| --- | --- | --- |
| 主な処理は読み取り・集計か | はい | いいえ、細かい更新が中心 |
| データはファイルや外部DBから来るか | はい | すでにアプリDB内で完結している |
| ローカルやバッチで処理できるか | はい | 常時多数ユーザーが更新する |
| 出力はParquetやレポートか | はい | アプリの正本状態そのもの |
| 権限管理や監査をDBに任せたいか | いいえ | はい |
| チームはSQLでレビューしたいか | はい | Pythonコード中心の方が自然 |

この質問により、DuckDBを入れる場所が見えてきます。

DuckDBを採用する最も安全な入り口は、既存システムを置き換えることではありません。既存DBやファイルの横に置き、検証・分析・変換の処理をDuckDBへ切り出すことです。

## このチュートリアルで扱わないこと

学習範囲を明確にするため、このチュートリアルで扱わないことも書いておきます。

扱わないこと:

- DuckDBをWebアプリのメインDBとして運用する方法
- 多数ユーザーによる同時更新設計
- 厳密な権限管理をDuckDBだけで完結させる設計
- 組織全体のDWHをDuckDBだけで置き換える設計
- ストリーミング処理基盤としての使い方

代わりに扱うこと:

- バラバラなファイルをSQLで読む
- raw/staging/martで責務を分ける
- 不正データを分類する
- 正常データをParquetへ出す
- Python/Node.jsから品質チェック結果を使う
- 外部DBやS3を読み取り専用で参照する

この線引きができると、DuckDBを過小評価せず、過大評価もしない状態で使えます。

## 環境構築

まずCLIを用意します。

```bash
duckdb --version
```

未インストールなら、macOSでは次を使います。

```bash
brew install duckdb
```

Python環境でCLIも使いたい場合:

```bash
pip install duckdb
```

最初のSQLを実行します。

```bash
duckdb
```

```sql
SELECT 42 AS answer;
```

期待する出力は、`answer` 列に `42` が表示されることです。ここではDBサーバーも設定ファイルも不要です。

この小さな体験で見るべき点は、SQLを実行するためにPostgreSQLサーバーもDocker Composeも不要だということです。DuckDBは、手元のプロセスでSQLを動かせます。

## よくあるつまずき

DuckDBはPostgreSQLのように常駐サーバーを起動するものだと思うと混乱します。まずは「SQLでファイルを読む分析エンジン」と考えてください。

CSVを読む前にテーブルを作らなければならない、という思い込みも不要です。DuckDBではファイルを直接 `SELECT` できます。正式なテーブル化は、構造や品質を確認してからで構いません。

もう1つのつまずきは、DuckDBが便利すぎるために、業務DBの責務まで持たせてしまうことです。DuckDBに置くべきなのは、分析・検証・変換のためのデータです。アプリの正規データは、PostgreSQLなどの責務として分けます。
