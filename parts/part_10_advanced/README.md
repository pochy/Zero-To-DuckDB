# Part 10: 専門家向けトピック

## このPartでできるようになること

DuckDBの拡張機能、Lakehouse連携、セキュリティ、限界を理解し、実務で採用すべきか判断できるようになります。

このPartの目的は、DuckDBでできることを増やすことではありません。「DuckDBでできる」と「DuckDBに任せるべき」を分けて考えることです。

ここまでのPartで、DuckDBはCSV、Excel、JSON、SQLite、PostgreSQL、HTTP、S3、Parquet、Python、Node.jsと連携できることを見ました。便利になるほど、すべてをDuckDBに寄せたくなります。しかし、専門家として重要なのは、境界を引く判断です。

## このPartの設計思想

専門家向けトピックの思想は、「DuckDBでできること」を増やすのではなく、「DuckDBに任せるべき責務」を見極めることです。

DuckDBは多くのことができます。だからこそ、できるという事実だけで採用判断をしてはいけません。正本管理、同時更新、権限、監査、大規模共有、SLAが必要なら、別の基盤と責務を分けるべきです。

## なぜこの考え方が必要なのか

便利な道具は、責務が膨らみやすいです。最初はCSV検証のために導入したDuckDBが、いつの間にかマスタ管理、アプリ状態、権限管理、全社DWHの代替まで背負うと、設計が崩れます。

専門家の仕事は、道具の能力を誇ることではありません。影響範囲を小さく保ち、壊れた時に説明でき、別基盤へ移す境界を残すことです。

## 初心者が誤解しやすいこと

初心者は、DuckDBがPostgreSQLやS3を読めると、DuckDBがそれらの代わりになると考えがちです。読めることと、正本として管理できることは違います。

また、拡張機能を `INSTALL` できることを運用可能と混同しがちです。本番では、ネットワーク制限、拡張の配布、資格情報、監査、アクセス制御を考える必要があります。

## プロはどう判断するか

プロは、DuckDBを小さく始めます。ローカル分析、品質チェック、Parquet検証、Notebook前処理、バッチの一部。価値が確認できてから、境界を保ったまま拡張します。

採用判断では、「DuckDBで実装できるか」ではなく、「DuckDBをここに置くと責務が自然か」を問います。自然でなければ、PostgreSQL、DWH、Lakehouse、Spark、Trinoなどと役割を分けます。

## 背景にある設計原則

専門家判断の背景にある原則は、道具を中心に設計しないことです。DuckDBが強力だからDuckDB中心にするのではなく、データの正本性、更新頻度、同時実行、権限、監査、データ量、運用体制を見て、自然な責務を割り当てます。

DuckDBは、単一プロセスで高速に分析できることが強みです。この強みは、ローカル検証、前処理、品質チェック、Parquet確認では大きな価値になります。一方で、組織全体の権限管理や多数ユーザーの同時更新を担わせると、強みではない領域に踏み込みます。

ここでのトレードオフは、導入の軽さと責務の重さです。DuckDBは軽く導入できます。しかし、軽く入れた道具に重い責務を持たせると、後で運用が苦しくなります。軽く始め、責務を小さく保ち、必要なら別基盤と分担する。これが専門家としての使い方です。

## まず知るべき言葉

- extension: DuckDBの追加機能
- Lakehouse: オブジェクトストレージ上のテーブル管理基盤
- Iceberg/Delta: 大規模データレイクのテーブル形式
- governance: 権限、監査、管理の仕組み
- concurrency: 同時実行性
- blast radius: 障害や変更の影響範囲
- least privilege: 必要最小限の権限だけ与える考え方
- source of truth: 正本となるデータの置き場所

## 専門家の判断軸

DuckDB採用を考えるとき、次の問いを使います。

- 処理はOLAPか、OLTPか
- データ量はローカルまたは単一ノードで扱えるか
- 同時書き込みが必要か
- 権限管理や監査をどこで行うか
- 正本データはどこに置くか
- 失敗時の影響範囲はどこまでか
- チームはSQLとして保守できるか
- 後続システムへ何を成果物として渡すか

DuckDBは非常に強力ですが、アーキテクチャの中心に置くべきか、周辺の分析・変換エンジンとして置くべきかは別問題です。

このチュートリアルでは、DuckDBを中心DBではなく、ファイル処理、品質チェック、正規化、Parquet出力のエンジンとして配置しています。

## 拡張機能

DuckDBは拡張機能で、Excel、SQLite、PostgreSQL、HTTP/S3などを扱えます。

```sql
INSTALL httpfs;
LOAD httpfs;
```

拡張機能は、DuckDBの守備範囲を広げます。このチュートリアルでも、次の拡張を使っています。

| 拡張 | 用途 |
| --- | --- |
| `excel` | Excelファイルを読む |
| `sqlite` | SQLiteマスタを読む |
| `postgres` | PostgreSQLマスタを読む |
| `httpfs` | HTTP/S3上のParquetを読む |

発展的には、次の拡張も検討対象になります。

| 拡張 | 用途 |
| --- | --- |
| `spatial` | 地理空間データを扱う |
| `fts` | 全文検索を扱う |
| `vss` | ベクトル類似検索を扱う |
| `iceberg` | Iceberg tableを読む |
| `delta` | Delta Lake形式を読む |
| `ducklake` | DuckDB中心のLakehouse管理を試す |

これらは便利ですが、標準チュートリアルの必須経路には入れません。理由は、学習環境、データ規模、運用責務が一気に複雑になるからです。まずは、CSV、Excel、JSON、SQLite/PostgreSQL、HTTP/S3、Parquetという中心経路を固めます。

拡張機能は便利ですが、運用では確認すべきことがあります。

- 本番環境で `INSTALL` できるか
- ネットワーク制限下で拡張を取得できるか
- 使用が許可された拡張か
- バージョンをどう固定するか
- 外部URLやS3へアクセスする権限をどう制御するか

学習環境では `INSTALL` で済んでも、本番環境ではネットワークが閉じていることがあります。その場合、拡張の配布方法や事前インストールを考えます。

## 拡張機能と攻撃面

拡張機能を使うと、DuckDBがアクセスできる範囲が広がります。HTTPやS3を読めるようになるということは、SQLから外部ネットワークへアクセスできる可能性があるということです。

実務では、次を確認します。

- 誰がSQLを実行できるか
- SQLからどのファイルを読めるか
- SQLからどのURLへアクセスできるか
- 認証情報をどこに置くか
- ログに秘密情報が残らないか

DuckDB自体が軽量でも、実行するSQLに強い権限があればリスクは大きくなります。SQL実行環境そのものを信頼境界として考えます。

## Lakehouseとの関係

DuckDBはParquetやHTTP/S3と相性がよいため、ローカルまたは小規模なLakehouse作業に向いています。

Lakehouseとは、S3のようなオブジェクトストレージ上にParquetなどを置き、テーブル形式やカタログで管理する考え方です。DuckDBは、そうしたファイルを読むエンジンとして使えます。

ただし、チーム全体で巨大なデータレイクを運用し、履歴管理、同時更新、権限、監査、カタログ連携を行う場合は、Iceberg、Delta、DuckLake、Trino、Spark、DWHなどとの役割分担を考えます。

Iceberg、Delta、DuckLakeは「Parquetファイルを読む」だけの話ではありません。テーブルとしての履歴、スキーマ進化、メタデータ、複数ユーザーでの運用を扱うための仕組みです。

このチュートリアルでは、深追いしすぎません。目的は、DuckDB単体のParquet datasetで十分な場面と、Lakehouse形式や中央DWHを検討すべき場面を分けられるようにすることです。

DuckDBが向いているLakehouse周辺の作業:

- ローカルでParquet datasetを検証する
- S3上の一部データをSQLで調べる
- パイプライン前後の品質チェックを行う
- Notebook前の重いJOINや集計を済ませる
- 小中規模のデータマートを作る

別の基盤を検討する場面:

- 多人数が同時にテーブルを更新する
- テーブル履歴やタイムトラベルを厳密に管理する
- 組織全体の権限管理が必要
- 数十TB以上のデータを継続的に共有する
- SLA付きの中央分析基盤が必要

## セキュリティと安全な運用

DuckDBはローカルプロセス内で動くため、実行するSQL、読み込むファイル、拡張機能、外部URLに注意します。

実務で確認すること:

- 信頼できないSQLをそのまま実行しない
- 外部URLやS3パスを入力値から直接組み立てない
- 認証情報をSQLファイルに直書きしない
- 読み取り専用接続を使う
- 出力ファイルに個人情報や機密情報を残さない
- `.duckdb` ファイルやParquetの保存先を制御する
- Notebookに秘密情報を残さない

Part 7で扱ったS3設定では、学習用にMinIOの固定認証情報をSQLに書いています。これはローカル学習環境だから許される簡略化です。本番では、環境変数、シークレット管理、IAMロールなどを検討します。

## read-onlyとleast privilege

このチュートリアルでは、SQLiteやPostgreSQLを `READ_ONLY` でATTACHします。

これは単なる安全策ではなく、責務分離です。

```text
正本DB: 更新と権限管理を担う
DuckDB: 読み取り、検証、変換を担う
```

least privilegeの考え方では、パイプラインには必要最小限の権限だけを与えます。カテゴリマスタを読むだけなら、更新権限は不要です。

不要な権限を持つと、SQLのバグや誤操作で正本データを壊す可能性が増えます。権限を絞ることは、信頼性の一部です。

## DuckDBの限界

DuckDBは万能DBではありません。

- 多数ユーザーの同時書き込みには向かない
- WebアプリのメインDBではない
- 水平分散DBではない
- DWHほどの権限管理や監査機能はない
- 大規模組織の中央分析基盤は別途検討する
- 長期的な正本データ管理は別システムと分担する

プロらしい判断は「DuckDBでできるか」ではなく、「DuckDBに任せるべきか」です。

たとえば、DuckDBでHTTP上のParquetを読めます。しかし、毎回本番APIから直接巨大データを読んでよいとは限りません。DuckDBでPostgreSQLを読めます。しかし、アプリの更新処理までDuckDBに寄せるべきではありません。

能力と責務を分けることが重要です。

## 使い分けの判断

DuckDBを選ぶべき場面:

- ローカルでCSV/Parquetを分析したい
- バッチでファイルを正規化したい
- Notebook前に重いJOINや集計を済ませたい
- CIではなくローカルで品質チェックを再現したい
- PostgreSQLやS3のデータを一時的に分析したい
- アプリに渡す前のデータ品質を検証したい
- Parquet datasetを作る小中規模パイプラインを組みたい

別の基盤を検討すべき場面:

- 多数ユーザーが同時に更新する
- 厳密な権限管理・監査が必要
- 数十TB以上を継続的にチーム共有する
- SLA付きのDWH運用が必要
- ストリーミング処理が中心
- 低レイテンシのオンラインAPI応答が中心
- 業務トランザクションの正本を管理する

判断に迷ったら、DuckDBを「正本」ではなく「検証・変換・分析の作業エンジン」として置けないかを考えます。その配置なら、多くの場面で安全に導入できます。

## アーキテクチャ上の配置例

安全な配置:

```text
PostgreSQL / S3 / CSV
      ↓
DuckDB batch
      ↓
quality report / Parquet / JSON
      ↓
BI / Notebook / Web API / ML
```

危険になりやすい配置:

```text
Webアプリ
  ↓
DuckDBを注文・ユーザー・権限の正本DBにする
```

前者では、DuckDBは入力を読み、検証し、成果物を出します。後者では、DuckDBがOLTP DBの責務を背負ってしまいます。

## 採用判断のケーススタディ

ここで、いくつかのケースを考えます。

### ケース1: 毎週届くCSVを検証したい

状況:

- メーカーからCSVが届く
- 価格不正やカテゴリ不一致を見たい
- 出力はParquetでよい
- 同時更新は不要

判断:

DuckDBに向いています。ファイルを直接読み、raw/staging/martで品質チェックし、正常データをParquetへ出せます。PostgreSQLやDWHへ入れる前の検証エンジンとして使うのが自然です。

### ケース2: ECサイトの注文DBを作りたい

状況:

- ユーザーが同時に注文する
- 決済状態を更新する
- 在庫を更新する
- トランザクションとロックが重要

判断:

DuckDBをメインDBにするべきではありません。PostgreSQLなどのOLTP DBを使います。DuckDBは、注文データを後で集計したり、Parquetへ変換したりする分析側で使います。

### ケース3: S3上のParquetをNotebookで調査したい

状況:

- S3にParquet datasetがある
- 一部カテゴリだけ見たい
- ローカルでSQL分析したい
- Notebookで可視化したい

判断:

DuckDBは有力です。`httpfs` でS3を読み、必要列と条件で絞り、集計結果だけNotebookへ渡します。ただし、資格情報、ネットワーク、読み取り権限には注意します。

### ケース4: 全社DWHを置き換えたい

状況:

- 複数部署が同時に使う
- 厳密な権限管理が必要
- 監査ログが必要
- 数十TB以上を継続運用する

判断:

DuckDB単体で置き換えるのは慎重に考えるべきです。BigQuery、Snowflake、ClickHouse、Trino、Spark、Lakehouse系基盤などを含めて検討します。DuckDBは、ローカル検証、開発、品質チェック、サブパイプラインで使う方が自然です。

## DuckDBを導入する時の段階的アプローチ

DuckDBを実務へ入れるなら、いきなり中心基盤にしない方が安全です。

段階的な導入:

1. ローカル分析で使う
2. 既存CSV/Parquetの品質チェックに使う
3. Notebook前の前処理に使う
4. バッチでParquet出力する
5. アプリやCLIへJSON契約を渡す
6. 外部DBやS3を読み取り専用で参照する

この順番なら、既存システムを壊さずにDuckDBの価値を確認できます。

避けたい導入:

```text
既存DBをいきなりDuckDBへ置き換える
アプリの書き込み先をDuckDBにする
権限管理を後回しにする
外部URLやS3を自由入力で読ませる
```

DuckDBは導入が簡単だからこそ、責務範囲を小さく始めます。

## データガバナンスの観点

DuckDBを使う処理でも、データガバナンスは必要です。

確認すること:

- どのデータを読んでよいか
- 誰がSQLを実行できるか
- 出力ファイルをどこに置くか
- 個人情報や機密情報を含むか
- 出力を誰に共有してよいか
- どのbatchのデータか追跡できるか
- いつ削除するか

DuckDBはローカルで簡単にParquetやCSVを出せます。これは強みですが、機密データを簡単に複製できるということでもあります。

実務では、出力ファイルの保存先と共有範囲を設計します。特にNotebookやレポートは、意図せずデータを残しやすい場所です。

## パフォーマンス限界の見極め

DuckDBは単一ノードで非常に強力ですが、単一ノードであることは意識します。

限界が見え始める兆候:

- ローカルメモリに収まらない
- 一時領域のI/Oが大きい
- 1台のCPUでは処理時間が許容できない
- 外部ストレージ読み取りがボトルネックになる
- チーム全員が同じ大規模処理を繰り返している
- 同時実行や共有運用が必要になる

この場合、DuckDBを捨てるのではなく、役割を変えます。

- 開発・検証はDuckDB
- 本番大規模処理はDWH/Spark/Trino
- 品質チェックの小さなサンプルはDuckDB
- 出力検証やローカル再現はDuckDB

DuckDBは、大規模基盤と競合するだけではありません。大規模基盤の周辺で、開発効率と検証性を上げる道具にもなります。

## 専門家レビューの観点

DuckDB採用や設計をレビューするときは、次を確認します。

- OLAP用途として使っているか
- 正本DBの責務を持たせていないか
- 外部DBはread-onlyか
- 秘密情報をSQLに直書きしていないか
- 拡張機能の利用が本番環境で許可されているか
- 出力ファイルの保存先と共有範囲が決まっているか
- データ量が単一ノードで扱えるか
- 失敗時の影響範囲が小さいか
- 後でDWHやLakehouseへ移せる境界になっているか

このレビュー観点を持つと、DuckDBの便利さに流されず、適切な責務に閉じ込められます。

## よくあるつまずき

DuckDBが便利になるほど、すべてDuckDBに寄せたくなります。しかし、便利なローカル分析エンジンと、組織の中央DB/DWHは役割が違います。

セキュリティでは、DBそのものよりも「誰がどのSQLを実行できるか」「どのファイルへアクセスできるか」が重要になります。

拡張機能を使うとき、開発環境で動いたことだけを根拠に本番採用してはいけません。ネットワーク、権限、配布方法、監査を確認します。

Lakehouse連携では、DuckDBがファイルを読めることと、テーブル管理・権限管理・履歴管理を担うことを混同しないようにします。

dbt、Dagster、dltのような周辺ツールも同じです。導入すれば自動的に良いパイプラインになるわけではありません。SQLの責務、入力契約、品質チェック、出力契約が曖昧なままでは、道具を増やしても複雑さが増えるだけです。
