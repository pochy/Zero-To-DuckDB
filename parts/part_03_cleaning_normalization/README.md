# Part 3: データクリーニングと正規化

## このPartでできるようになること

汚い商品データを、分析や出力に使える標準スキーマへ変換できるようになります。欠損、空白、価格の型崩れ、カテゴリ不一致、重複を扱います。

このPartの主題は、文字列を少し整えることではありません。raw層に受けたデータを、どこまで機械的に直し、どこから品質問題として扱うかを設計することです。

実務では、入力データは必ず汚れています。重要なのは、汚れをゼロにすることではなく、汚れを分類し、説明できる形にすることです。

## このPartの設計思想

クリーニングと正規化の思想は、「データをきれいにする」ことではなく、「どこまで機械的に直し、どこから品質問題として扱うかを分ける」ことです。

空白を消す、空文字をNULLにする、大文字小文字をそろえる。これらは入力の意味を大きく変えない機械的な正規化です。一方で、未知カテゴリを既存カテゴリへ寄せる、欠損価格を0にする、重複行を選ぶ、といった処理は業務判断を含みます。

このPartでは、SQL関数を覚えるのではなく、機械的な正規化と業務判断の境界を見ます。

## なぜこの考え方が必要なのか

不正データを前にした時、処理を止めるだけでは全体像が見えません。逆に、すべてを自動修正すると、間違ったデータを正常に見せかける危険があります。

`try_cast` は、この中間にあります。変換できない価格で処理を止めず、NULLとして分類し、品質チェックへ渡します。これは「不正を許す」ためではなく、「不正を観察可能にする」ための設計です。

`LEFT JOIN` も同じです。未知カテゴリを落とさず残すことで、マスタ不一致を品質問題として見えるようにします。INNER JOINで落とすと、きれいな表はできますが、問題は消えたのではなく見えなくなっただけです。

## 初心者が誤解しやすいこと

初心者は、NULLを失敗、エラー行を邪魔な行、重複を消すべきノイズとして扱いがちです。しかし実務では、NULLやエラー行はデータ品質を説明するための重要な信号です。

また、`DISTINCT` で重複を消せばよいと考えがちです。重複排除は技術処理ではなく業務判断です。どの行を正とするか、なぜその行を残すかを説明できなければ、後で結果を信頼できません。

## プロはどう判断するか

プロは、正規化ルールを三つに分けます。

- 機械的に安全なルール
- 品質チェックとして分類するルール
- 業務判断として別途管理すべきルール

この分離により、SQLが単なる変換手順ではなく、品質判断の記録になります。`trim`、`nullif`、`try_cast`、`LEFT JOIN`、`row_number()` は、ただの関数ではありません。入力をどう解釈し、どこまで信頼し、どこから説明責任を持つかを表す設計判断です。

## 背景にある設計原則

正規化の背景にある原則は、入力の意味を勝手に決めすぎないことです。空白除去や空文字のNULL化は、ほとんどの場合、意味を変えずに機械処理しやすくする操作です。一方、未知カテゴリを既存カテゴリへ寄せる、欠損価格を補完する、重複行の優先順位を変える、といった操作は業務上の解釈を含みます。

この違いを分けないと、SQLがブラックボックスになります。何が単なる整形で、何が業務判断なのか分からなくなります。後から品質問題が起きた時、SQLを書いた本人しか理由を説明できません。

このPartでは、stagingを「正しいデータだけを置く場所」とは考えません。stagingは、rawを分析可能な形へ解釈する場所です。解釈できなかったものはNULLや未照合として残し、martの品質チェックへ渡します。つまり、正規化は問題を消す工程ではなく、問題を分類可能にする工程です。

## まず知るべき言葉

- cleaning: 空白除去、型変換、表記ゆれ修正
- normalization: 標準スキーマへそろえること
- raw layer: 入力の痕跡を残す層
- staging layer: 型や表記を標準化する層
- mart layer: 分析や出力に使う層
- master data: カテゴリなどの基準データ
- error row: 品質チェックに引っかかった行
- deduplication: 重複排除
- deterministic: 同じ入力なら同じ結果になること

## raw、staging、martを分ける理由

このチュートリアルでは、データを大きく3段階に分けます。

```text
raw      入力を落とさず受ける
staging  型、表記、マスタ照合、重複優先順位を整える
mart     品質レポートや出力用データを作る
```

この分離は、単なるフォルダ分けや命名ルールではありません。責務を分けるための設計です。

raw層では、入力の事実を残します。価格が `N/A` なら、勝手に0にはしません。カテゴリが未知なら、勝手に既存カテゴリへ寄せません。ファイル名や取り込み日も残します。

staging層では、分析しやすい型と表記に変換します。空白を消し、空文字をNULLにし、価格を数値化し、カテゴリ名を小文字にそろえます。ただし、変換できないものを無理に補正するのではなく、NULLや未照合として残します。

mart層では、判断に使うテーブルを作ります。品質チェック結果、エラー行、正規化済み出力などです。mart層は、他の人や他のシステムが見る前提の層です。

初心者がやりがちな失敗は、raw層でいきなり最終形を作ろうとすることです。そうすると、どの段階で何を変えたのか分からなくなります。

## 手順1: rawからstagingへ変換する

完成例の中心は `sql/03_normalize.sql` です。

```bash
cd product-data-duckdb
sed -n '1,180p' sql/03_normalize.sql
```

重要な変換は次の部分です。

```sql
nullif(trim(jan_code), '') AS jan_code,
nullif(trim(product_name), '') AS product_name,
try_cast(nullif(trim(price), '') AS INTEGER) AS price,
lower(nullif(trim(category_name), '')) AS category_name
```

この4行には、実務データ処理の基本が詰まっています。

| 処理 | 目的 |
| --- | --- |
| `trim(...)` | 前後の余計な空白を消す |
| `nullif(..., '')` | 空文字をNULLとして扱う |
| `try_cast(... AS INTEGER)` | 変換できる価格だけ数値にする |
| `lower(...)` | 大文字小文字の表記ゆれを抑える |

`trim` は地味ですが重要です。`'food'` と `' food '` は、人間には同じに見えても、SQL上は別の文字列です。JOINやGROUP BYでは、この違いが結果を壊します。

`nullif(trim(...), '')` は、空白だけの値をNULLへ寄せます。空文字とNULLが混在すると、欠損チェックが複雑になります。欠損はNULLとして扱う、というルールをstaging層で作ります。

`try_cast` は、汚い入力を扱うときの重要な道具です。通常の `CAST` は変換できない値で処理が止まります。`try_cast` は変換できない場合にNULLを返します。

つまり、`try_cast` は不正データを無視するためのものではありません。不正データを「変換失敗」として品質チェックに渡すためのものです。

## CASTではなくtry_castを使う理由

価格列に次のような値が混ざっているとします。

```text
1200
800
N/A
-100
未定
```

`CAST(price AS INTEGER)` を使うと、`N/A` や `未定` で処理が止まります。処理が止まること自体は、厳密なシステムでは良い場合もあります。しかし、実務の初期取り込みでは、まず全体の品質を見たいことが多いです。

`try_cast(price AS INTEGER)` なら、変換できない値はNULLになります。その後で、次のように品質チェックできます。

```sql
WHERE price IS NULL OR price < 0
```

この設計の利点は、エラーを1件見つけて止まるのではなく、全体で何件、どのファイルに、どんな種類の問題があるかを集計できることです。

不正データを処理に通すのではなく、不正データを分類できる形で残す。これがこのPartの中心です。

## 手順2: マスタとJOINする

カテゴリ名をカテゴリマスタと照合します。

```sql
CREATE OR REPLACE TABLE staging.products_with_category AS
SELECT
  p.*,
  c.category_id
FROM staging.normalized_products p
LEFT JOIN master.categories c
  ON p.category_name = c.category_name;
```

ここで `LEFT JOIN` を使っている点が重要です。

`INNER JOIN` を使うと、マスタに存在しないカテゴリの行が落ちます。一見きれいな結果になりますが、未知カテゴリが何件あったのか分からなくなります。

`LEFT JOIN` では、入力側の商品行を残したまま、マスタに一致した場合だけ `category_id` が入ります。一致しない場合は `category_id` がNULLになります。

このNULLは失敗ではありません。品質チェックのための信号です。

```sql
WHERE category_id IS NULL
```

で未知カテゴリを抽出できます。

## マスタ照合の考え方

マスタは、正しさの基準です。カテゴリ名、メーカーID、店舗ID、部署コードなど、入力データだけでは正しいか判断できないものを照合するために使います。

ただし、マスタ照合には注意があります。

- 入力側の表記ゆれをどこまで吸収するか
- マスタにない値を自動追加してよいか
- 旧カテゴリや廃止カテゴリをどう扱うか
- ひらがな、カタカナ、英語表記をどう寄せるか
- マスタ側が間違っている可能性をどう扱うか

このチュートリアルでは、まず `lower(trim(category_name))` で小文字化と空白除去だけを行います。これは、安全な正規化です。

一方で、`food` を `foods` に寄せる、`食品` を `food` に寄せる、といった処理は、業務ルールが必要です。勝手に直すと、別の意味のカテゴリまで統合してしまう危険があります。

## 手順3: 品質チェックする

完成例では `sql/04_quality_checks.sql` が品質レポートを作ります。

```bash
make run
make quality
```

見るべきチェックは次の通りです。

- JANコード欠損
- 商品名欠損
- 価格不正
- 未知カテゴリ
- JANコード重複

品質チェックは、処理の最後におまけで見るものではありません。実務では、出力を信頼してよいか判断するための契約です。

完成実装では、品質チェック結果を `mart.quality_report` に保存します。これは、単に画面へ表示して終わるよりも重要です。テーブルとして残すことで、PythonやNode.jsのチェックCLI、HTMLレポート、テストから同じ結果を参照できます。

品質チェックは、次の問いに答えるためのものです。

- このデータを後続処理に渡してよいか
- どの種類の問題が多いか
- 問題は特定のメーカーやファイルに偏っているか
- 取り込みルールを変えるべきか
- 入力元へ差し戻すべきか

## 手順4: 重複を扱う

完成例では、JANコードごとに最新行を選びます。

```sql
row_number() OVER (
  PARTITION BY jan_code
  ORDER BY ingest_date DESC, updated_at DESC, source_file DESC
) AS row_priority
```

このSQLは、JANコード単位で行を並べ、優先順位を付けています。

| 指定 | 意味 |
| --- | --- |
| `PARTITION BY jan_code` | JANコードごとにグループを分ける |
| `ORDER BY ingest_date DESC` | 新しい取り込み日を優先する |
| `updated_at DESC` | 入力元で新しい更新日を優先する |
| `source_file DESC` | それでも同じならファイル名で順序を固定する |

重複排除で最も危険なのは、「なんとなく1件にする」ことです。

SQLで `SELECT DISTINCT` を使うだけでは、どの行が残るのか、なぜ残るのかを説明できない場合があります。実務では、重複があったときにどの行を正とするかを明示する必要があります。

このチュートリアルでは、次の考え方にしています。

1. 新しい取り込みを優先する
2. 入力元の更新日が新しいものを優先する
3. 最後にファイル名で順序を固定し、再実行時の結果を安定させる

最後の `source_file DESC` は、業務的な優先順位として強い意味があるわけではありません。しかし、同点のときに結果を安定させるために入れています。同じ入力なら同じ結果になることは、テストや運用で重要です。

## 手順5: エラー行を出力する

```bash
ls reports
```

`reports/product_errors.csv` は、品質チェックに引っかかった行を確認するためのファイルです。

品質レポートの件数だけでは、実務上の対応はできません。

```text
invalid_price: 4
unknown_category: 4
```

という件数が分かっても、どのファイルのどの行が悪いのかが分からなければ、入力元へ差し戻せません。

そのため、完成実装では `mart.product_errors` を作り、エラー理由を `error_reasons` にまとめています。

```sql
concat_ws(
  ',',
  CASE WHEN jan_code IS NULL THEN 'missing_jan_code' END,
  CASE WHEN product_name IS NULL THEN 'missing_product_name' END,
  CASE WHEN price IS NULL OR price < 0 THEN 'invalid_price' END,
  CASE WHEN category_id IS NULL THEN 'unknown_category' END
) AS error_reasons
```

1行に複数の問題がある場合もあります。たとえば、価格が不正でカテゴリも未知、という行です。エラー理由を列として残すと、後から問題の種類別に集計したり、入力元へ具体的に返したりできます。

## クリーニングでやってよいこと、危険なこと

すべての修正を同じように扱ってはいけません。

安全に行いやすい処理:

- 前後空白を消す
- 空文字をNULLにする
- 大文字小文字をそろえる
- 日付や数値へ変換できるものだけ変換する
- マスタと一致したIDを付ける

慎重に扱うべき処理:

- カテゴリ名を推測で置き換える
- 欠損価格を0で埋める
- 重複行を理由なく削除する
- 不明なJANコードを生成する
- 入力元ファイル名を捨てる

前者は、入力の意味を大きく変えず、機械処理しやすくするための正規化です。後者は、業務判断を含みます。業務判断をSQLに入れる場合は、なぜそうするのかを説明できる必要があります。

## 品質問題を分類する考え方

品質問題は、すべて同じ深刻度ではありません。

たとえば、次の問題を考えます。

- 商品名の前後に空白がある
- 価格が `N/A` になっている
- JANコードが欠損している
- カテゴリがマスタに存在しない
- 同じJANコードが複数ファイルに存在する
- 価格が負数になっている

これらは、対応方針が違います。

| 問題 | 分類 | 対応 |
| --- | --- | --- |
| 前後空白 | 機械的に直せる表記ゆれ | `trim` する |
| 空文字 | 欠損表現の揺れ | NULLへ寄せる |
| `N/A` 価格 | 型変換失敗 | NULLにして品質チェック |
| JAN欠損 | 識別子欠損 | エラー行として扱う |
| 未知カテゴリ | マスタ不一致 | エラー行として扱う |
| 重複JAN | 優先順位設計が必要 | `row_number()` で選ぶ |
| 負数価格 | 業務ルール違反 | エラー行として扱う |

この分類がないと、すべてを「汚いデータ」と呼ぶだけになります。実務では、問題の種類ごとに対応者が違うこともあります。

- 入力元メーカーへ差し戻す問題
- マスタ管理者へ確認する問題
- パイプライン側で吸収できる問題
- 業務ルールを決め直す問題

品質チェックは、単にエラー件数を出すためではありません。次のアクションを決めるための分類です。

## 標準スキーマを設計する

正規化では、最終的にどの列を標準スキーマとするかを決めます。

このチュートリアルの標準的な商品列は次の通りです。

```text
jan_code
product_name
price
category_name
category_id
maker_name
updated_at
source_file
batch_id
ingest_date
```

この列一覧には、業務データとメタデータが混ざっています。

業務データ:

- `jan_code`
- `product_name`
- `price`
- `category_name`
- `category_id`
- `maker_name`
- `updated_at`

メタデータ:

- `source_file`
- `batch_id`
- `ingest_date`

初心者は、メタデータを軽視しがちです。しかし、実務ではメタデータが原因調査に効きます。

たとえば、出力後に「この商品価格はなぜこの値なのか」と聞かれたとします。`source_file` と `batch_id` があれば、どの入力ファイルのどの取り込みから来たかを追えます。これがなければ、正規化後の値だけが残り、説明が難しくなります。

## 正規化ルールをどこまでSQLに書くか

正規化ルールには、SQLに書いてよいものと、別管理した方がよいものがあります。

SQLに直接書きやすいもの:

- 空白除去
- 空文字のNULL化
- 小文字化
- 数値変換
- 日付変換
- マスタJOIN

別管理を検討するもの:

- カテゴリ名の同義語マッピング
- メーカーごとの特殊ルール
- 価格補正ルール
- 廃止カテゴリの扱い
- 優先メーカーの順位

ルールが少ないうちはSQLに直接書いても構いません。しかし、業務ルールが増えると、マッピングテーブルやマスタとして管理した方がよくなります。

たとえば、`食品`、`Food`、`foods`、`FOOD` をすべて `food` に寄せるだけならSQLでも書けます。しかし、カテゴリが100種類あり、各部署がルールを更新するなら、SQLにベタ書きするのは保守しにくくなります。

プロは、ルールが増えたときにどこへ逃がすかを考えます。

## 重複排除は業務判断である

`row_number()` を使えば、技術的には重複を1件にできます。しかし、どの行を残すかは業務判断です。

このチュートリアルでは、次の優先順位にしています。

```text
ingest_date DESC
updated_at DESC
source_file DESC
```

これは、「新しい取り込み」「入力元での新しい更新」「最後の安定的な順序」の順で優先するという考え方です。

しかし、実務では別の判断もあり得ます。

- 特定メーカーを優先する
- 価格がNULLでない行を優先する
- 商品名が長い行を優先する
- マスタ登録済みカテゴリの行を優先する
- 承認済みフラグのある行を優先する

どれが正しいかは業務によります。重要なのは、重複排除を暗黙にしないことです。

悪い例:

```sql
SELECT DISTINCT *
FROM staging.products_with_category;
```

このSQLでは、なぜその行が残るのか説明できません。

良い例:

```sql
row_number() OVER (
  PARTITION BY jan_code
  ORDER BY ingest_date DESC, updated_at DESC, source_file DESC
) AS row_priority
```

優先順位がSQLに現れているため、レビューできます。

## 品質チェックレビューの観点

品質チェックSQLをレビューするときは、次を確認します。

- チェック名が業務上理解できるか
- 件数だけでなくエラー行も出せるか
- エラー理由が複数ある行を扱えるか
- NULLと空文字を混同していないか
- 不正価格の定義が明確か
- マスタ不一致を落とさず残しているか
- 重複チェックの単位が明確か
- 出力対象から除外する条件と一致しているか

品質チェックは、後続のParquet出力やアプリ連携の信頼性を支えます。ここが曖昧だと、正常データとして出したものを後で説明できません。

## OCR confidenceはエラーではなく警告として扱う

AI-OCRやLLM抽出結果には、信頼度スコアが付くことがあります。このチュートリアルのJSON Linesにも `extraction.confidence` があり、raw取り込みでは `ocr_confidence` として残します。

ここで重要なのは、低いconfidenceを即エラーとして落とさないことです。

confidenceは「その行が間違っている」と断定する値ではありません。人間確認の優先度を上げるための品質信号です。価格が不正、JANコードが欠損、カテゴリが未知、という問題は出力可否に直結します。一方、confidenceが低い行は、他の必須項目が揃っていれば一旦出力できる場合もあります。

完成実装では、`low_ocr_confidence` を `mart.quality_report` に出しますが、`mart.product_errors` の除外条件には入れていません。これは、エラーと警告を同じものとして扱わないためです。

この判断は実務で重要です。すべての注意信号をエラーにすると、パイプラインは止まりやすくなります。逆に、注意信号を何も記録しないと、AI抽出の品質を改善できません。

## エラーを「止める」か「分類する」か

データ処理では、エラーを見つけたときに処理を止める設計と、エラーを分類して処理を続ける設計があります。

処理を止める方がよい場面:

- 必須マスタが読めない
- SQL自体が壊れている
- 出力先に書けない
- スキーマが根本的に違う
- 全データが空になっている

分類して続ける方がよい場面:

- 一部商品の価格が不正
- 一部JANコードが欠損
- 一部カテゴリが未知
- 重複候補がある
- 一部行だけ日付変換に失敗

このチュートリアルでは、行単位の品質問題は分類して続けます。なぜなら、全体の品質状況を見たいからです。一方、SQLファイルが実行できない、DBが作れない、Parquetが出力できないといった問題は、処理を止めるべきです。

この区別があると、パイプラインの失敗とデータ品質の失敗を混同しなくなります。

## よくあるつまずき

`CAST` を使うと不正な価格で処理が止まります。汚い入力を扱うときは `try_cast` を使い、変換失敗を品質チェックへ回す方が実務向きです。

`INNER JOIN` でマスタ不一致を落とすと、問題が見えなくなります。検証段階では `LEFT JOIN` で残し、後でエラーとして分類します。

重複排除を `DISTINCT` だけで済ませると、どの行が残ったのか説明しにくくなります。`row_number()` で優先順位を明示すると、再実行時にも結果を確認しやすくなります。

品質チェックを件数だけで終わらせると、次のアクションにつながりません。件数とエラー行の両方を出すことで、全体傾向と具体的な修正対象を両方見られます。

## DuckDBらしい列操作で正規化を短く書く

DuckDBには、列数が多い表を扱うための便利なSQLがあります。

- `SELECT * EXCLUDE`: 不要な列だけ除外する
- `SELECT * REPLACE`: 特定の列だけ変換して置き換える
- `COLUMNS`: 正規表現で複数列をまとめて選ぶ
- `SUMMARIZE`: テーブル全体のプロファイルを見る

完成実装では、次で例を作れます。

```bash
cd product-data-duckdb
make friendly-sql
```

`mart.friendly_clean_products` は `SELECT * EXCLUDE` と `SELECT * REPLACE` を使います。`mart.numeric_column_profile` は `COLUMNS` で価格やOCR confidenceのような数値列をまとめて見ます。`mart.normalized_profile` は `SUMMARIZE` で欠損率や最小・最大を確認します。

ただし、便利構文は読みやすさを壊すこともあります。後続が依存する本番SQLでは、明示的な列名の方がレビューしやすい場合があります。このチュートリアルでは、raw/staging/martの中心SQLは明示列を基本にし、便利構文は発展例として扱います。
