# Part 6: Node.js / アプリケーション組み込み

## このPartでできるようになること

DuckDBで作った品質チェックをNode.jsやアプリケーションから呼び出す設計を理解します。ここではDBをアプリのメインDBにするのではなく、分析・検証処理をアプリから使う境界を学びます。

このPartの目的は、Node.jsからDuckDBを呼ぶ方法を1つ覚えることではありません。アプリケーションが何に依存してよく、何に依存しすぎると壊れやすいかを判断することです。

Part 5では、Pythonから品質チェック結果をJSONとして取得しました。Part 6では、同じ考え方をNode.jsアプリの境界として扱います。

## このPartの設計思想

アプリケーション組み込みの思想は、「アプリからDuckDBを直接自由に使う」ことではなく、「アプリが依存してよい境界を小さく固定する」ことです。

アプリは、DuckDB内部のraw、staging、mart、SQLファイル、品質ルールの詳細を知る必要はありません。アプリが必要なのは、品質チェックが成功したか、失敗理由は何か、どのbatchの結果か、後続処理に進んでよいかです。

## なぜこの考え方が必要なのか

アプリが内部SQLに密結合すると、SQL改善やテーブル構造変更がアプリ変更になります。逆に、JSON contractを境界にすれば、内部実装を変えても、アプリは安定したフィールドを見続けられます。

DuckDBはアプリに組み込めますが、アプリの正本DBとして置くべきではありません。このPartでは、DuckDBをアプリ状態の保存先ではなく、分析・検証結果を提供する裏側のエンジンとして扱います。

## 初心者が誤解しやすいこと

初心者は、Node.jsからコマンドを呼べたら組み込み完了と考えがちです。しかし、実務では呼び出し方よりも契約が重要です。JSONの形、exit code、失敗理由、同期/非同期、実行タイミングが決まっていなければ、アプリは安定して使えません。

また、WebリクエストのたびにDuckDBパイプラインを実行する設計も危険です。重い処理、ファイルロック、外部ソース接続、失敗時の再試行をリクエスト処理に混ぜると、アプリの信頼性が下がります。

## プロはどう判断するか

プロは、DuckDB処理をアプリの外側に置けないかをまず考えます。バッチで実行し、結果をJSONやParquetとして固定し、アプリはそれを読む。この構成なら、アプリの応答とデータ処理の失敗を分離できます。

直接呼ぶ場合でも、任意SQLを許さず、固定されたCLIやAPIを通します。アプリはDuckDBを知るのではなく、契約を知る。この分離が、アプリ組み込みの基本です。

## 背景にある設計原則

アプリ組み込みの背景にある原則は、内部実装と外部契約を分けることです。DuckDB内部では、raw、staging、mart、品質チェックSQL、Parquet出力など複数の要素が動きます。しかし、アプリがそれらすべてを知る必要はありません。アプリは、安定したJSON contractだけを見ればよい状態にします。

この分離により、SQLの改善、テーブル名の変更、品質チェックの追加を、アプリの大きな変更にせずに済みます。内部は変えられるが、契約は保つ。この考え方は、API設計と同じです。

ここでのトレードオフは、直接性と安定性です。アプリから直接SQLを実行すると柔軟ですが、内部構造に密結合します。CLIやAPIで契約を固定すると少し遠回りですが、変更に強くなります。実務では、後者の安定性が重要になる場面が多いです。

## まず知るべき言葉

- CLI boundary: アプリからコマンドを呼ぶ境界
- JSON contract: 入出力をJSONで固定する契約
- exit code: コマンドの成功・失敗を示す終了コード
- threshold: 許容するエラー件数の上限
- read-only access: 読み取り専用でDBを見ること
- coupling: アプリが内部実装に強く依存している状態
- API response: Web APIが返す構造化データ
- operational boundary: 運用上、責務を分ける境界

## アプリにDuckDBを組み込むとはどういうことか

DuckDBはアプリに組み込めます。ただし、「アプリのメインDBにする」という意味ではありません。

このチュートリアルで扱う組み込みは、次のような形です。

```text
入力ファイル
  ↓
DuckDBパイプライン
  ↓
品質チェック結果 / Parquet出力
  ↓
Node.jsアプリまたはCLIが読む
```

アプリは、DuckDB内部のraw/staging/martの全てを知る必要はありません。アプリが必要なのは、品質チェックが成功したか、どのチェックが何件失敗したか、出力行数がいくつか、といった判断可能な結果です。

そのため、このPartではJSON契約を重視します。

## 手順1: Node.js CLIを実行する

```bash
cd product-data-duckdb
make run
node scripts/check-quality.mjs --db product_pipeline.duckdb
```

このスクリプトはDuckDB CLIを呼び出し、品質チェック結果をJSONとして表示します。アプリ側はSQLの詳細を知らず、JSON契約だけを見ます。

出力には、次のようなフィールドがあります。

| フィールド | 意味 |
| --- | --- |
| `ok` | 指定された失敗条件に対して成功か |
| `totalErrors` | 品質エラーの合計件数 |
| `failingCheckCount` | 失敗しているチェック種類数 |
| `exportedRows` | 単一Parquet出力の行数 |
| `datasetRows` | カテゴリpartitioned datasetの行数 |
| `ingestDatasetRows` | 取り込み日partitioned datasetの行数 |
| `checks` | チェック名ごとのエラー件数 |
| `failingChecks` | エラー件数が1以上のチェックだけ |
| `failureReasons` | なぜ `ok` がfalseになったか |

この形にしておくと、Web API、バッチ、管理画面、テストが同じ契約に依存できます。

## なぜSQLではなくJSONに依存させるのか

アプリから直接 `mart.quality_report` を読ませる設計もできます。しかし、アプリがSQLの内部構造に依存しすぎると、変更が難しくなります。

たとえば、品質チェックの内部SQLを改善したいだけなのに、アプリ側のSQLも同時に修正する必要が出るかもしれません。

JSON契約を挟むと、境界が明確になります。

```text
SQL内部実装
  ↓
check-quality.mjs
  ↓
JSON contract
  ↓
アプリ
```

アプリは、`ok`、`totalErrors`、`checks` のような安定したフィールドだけを見ます。内部でどのSQLを実行しているか、どのテーブルから読んでいるかは隠せます。

この分離により、次の変更がしやすくなります。

- 品質チェックSQLを増やす
- Parquet出力の確認項目を追加する
- Python版とNode.js版の出力を揃える
- Web API化する
- しきい値を環境ごとに変える

## 手順2: エラー上限を設定する

```bash
node scripts/check-quality.mjs --db product_pipeline.duckdb --max-errors 20
```

エラー件数が上限を超えたら失敗にできます。実務では「エラーが1件でもあれば失敗」より、「警告として許容する範囲」を設計することがあります。

たとえば、移行直後のパイプラインでは、外部入力の品質が安定していないことがあります。その場合、まずはエラー件数を可視化し、一定件数を超えたら失敗にする設計が現実的です。

一方で、後続システムへ渡してはいけない重要項目では、1件でも失敗にする方が安全です。

失敗条件は、技術的な好みではなく、業務リスクで決めます。

| 条件 | 向いている場面 |
| --- | --- |
| `--fail-on-any-error` | 本番出力に不正データを混ぜたくない |
| `--max-errors 20` | 移行期や監視用途で一定件数まで警告扱いにする |
| しきい値なし | 手元で状況を観察するだけ |

## exit codeの意味

CLIはJSONを出すだけでなく、終了コードでも成功・失敗を返します。

`scripts/check-quality.mjs` では、次のように動きます。

- 成功なら `0`
- 品質条件により失敗なら `1`
- 引数不正や実行エラーなら `2`

この区別は、自動化で重要です。

```bash
node scripts/check-quality.mjs --db product_pipeline.duckdb --fail-on-any-error
```

このコマンドが失敗した場合、バッチやCIは処理を止められます。人間がJSONを読まなくても、機械的に判断できます。

ただし、ユーザーは以前CI不要と指定しています。このチュートリアルではCI実行までは求めず、ローカルCLIで同じ考え方を学びます。

## 手順3: アプリ境界を考える

Node.jsアプリからDuckDBを使う選択肢は複数あります。

- DuckDB公式クライアントを使う
- CLIを呼び出してJSONを受け取る
- 事前にParquetやCSVへ出力し、アプリは成果物だけ読む

それぞれの使い分けは次の通りです。

| 方法 | 利点 | 注意点 |
| --- | --- | --- |
| 公式クライアント | アプリ内から直接SQLを実行できる | アプリがSQLやDB構造に近くなる |
| CLI境界 | 依存が少なく、言語をまたいで使える | コマンド実行とエラー処理を設計する必要がある |
| 成果物だけ読む | アプリがDuckDBを知らなくてよい | パイプライン実行タイミングを別途管理する |

このチュートリアルでは、依存を増やさずにCLI境界で示します。重要なのは、アプリがSQLファイルや品質ルールに密結合しすぎないことです。

## `@duckdb/node-api` を直接使う選択肢

Node.jsからDuckDBを直接使いたい場合は、Node.js Neo clientの `@duckdb/node-api` が選択肢になります。公式docsでは、`DuckDBConnection.create()` で接続を作り、`connection.run()` や `runAndReadAll()` でSQLを実行する例が示されています。

最小例:

```ts
import { DuckDBConnection } from "@duckdb/node-api";

const connection = await DuckDBConnection.create();
const reader = await connection.runAndReadAll(`
  SELECT check_name, error_count
  FROM mart.quality_report
  ORDER BY check_name
`);

console.log(reader.getRowObjects());
```

直接APIを使う利点は、Node.jsプロセス内でDuckDBを扱えることです。低レイテンシに小さな分析を行いたい場合や、結果をチャンクで読みたい場合には便利です。

ただし、このチュートリアルの標準実装では、あえてCLI境界を採用しています。理由は、npm依存を増やさず、Python版やMakefileと同じDuckDB CLIを実行エンジンにできるからです。

直接APIを採用する場合でも、任意SQLをユーザーから受け取る設計にはしません。アプリは「品質チェック結果」という契約を呼ぶのであって、内部のraw/staging/martを自由に操作するべきではありません。

判断の目安:

| 選択肢 | 向いている場合 |
| --- | --- |
| CLI境界 | 依存を減らし、SQL本体をアプリから独立させたい |
| `@duckdb/node-api` | Node.jsプロセス内でDuckDBを直接扱う必要がある |
| 生成済みParquet/JSON参照 | アプリがDuckDBを知らなくてよい設計にしたい |

## 手順4: Web API化する場合の契約

品質チェックをAPIにするなら、レスポンスは次のような形にします。

```json
{
  "ok": false,
  "totalErrors": 11,
  "checks": {
    "invalid_price": 4,
    "unknown_category": 4
  },
  "failureReasons": ["quality_errors_present"]
}
```

APIが返すべきなのは、画面表示用の文章ではなく、アプリが判断できる構造化データです。

画面文言をAPIの中心にすると、フロントエンドや別システムが文字列解析に依存してしまいます。文字列は変わりやすく、翻訳や文言修正で壊れます。

API契約では、次のように分けます。

- 機械が判断するフィールド: `ok`、`totalErrors`、`checks`
- 人間向けの補足: `message`、`displayText`
- デバッグや監査用: `batchId`、`generatedAt`、`source`

このチュートリアルのCLIでは、まず機械が判断できるフィールドに絞っています。

## 手順5: アプリに組み込む時の注意

DuckDBファイルを複数プロセスから同時に書き換える設計は避けます。アプリから読むだけにする、またはパイプライン実行とアプリ参照を分ける方が安全です。

安全な構成:

```text
バッチ処理がDuckDBを更新する
  ↓
Parquet / JSON / レポートを出力する
  ↓
アプリは出力成果物または読み取り用DBを見る
```

危険な構成:

```text
WebリクエストごとにDuckDBへ書き込む
複数アプリプロセスが同じDuckDBファイルを更新する
アプリの注文状態やユーザー状態をDuckDBに保存する
```

DuckDBは分析・検証に使います。アプリの状態管理はPostgreSQLなどのOLTP DBに任せます。

## SQLインジェクションと入力パラメータ

アプリからSQLを組み立てる場合は、SQLインジェクションに注意が必要です。

このチュートリアルのNode.js CLIでは、ユーザー入力から複雑なSQLを組み立てていません。実行するSQLはスクリプト内で固定し、引数はDBファイルパスやしきい値に限定しています。

実務でAPIから条件を受け取る場合は、次を守ります。

- 任意のSQL文字列を受け取らない
- 許可されたパラメータだけを受け取る
- SQLファイルや固定クエリを正本にする
- 入力値をバリデーションする
- 書き込み権限をアプリに持たせすぎない

アプリ境界では、便利さよりも予測可能性が重要です。

## Webアプリに組み込む場合の設計例

品質チェック結果をWebアプリで見せる場合、典型的には次のような構成になります。

```text
バッチまたは管理者操作
  ↓
DuckDBパイプライン実行
  ↓
品質JSONを生成
  ↓
Web APIがJSONを返す
  ↓
管理画面が表示する
```

このとき、Webリクエストのたびに重いDuckDBパイプラインを実行する設計は避けます。リクエスト応答が遅くなり、同時アクセス時のロックや負荷も考える必要が出ます。

より安全な設計:

- パイプライン実行はバッチや管理者操作に限定する
- アプリは生成済みJSONやParquetを読む
- DBファイルは読み取り専用で参照する
- 実行中と参照中の成果物を分ける
- 最新結果の生成時刻を返す

APIレスポンスには、品質結果だけでなく、いつ作った結果かも入れると運用しやすくなります。

```json
{
  "ok": true,
  "generatedAt": "2026-05-10T09:00:00Z",
  "batchId": "batch_2026_05_10",
  "totalErrors": 11,
  "checks": {
    "invalid_price": 4,
    "unknown_category": 4
  }
}
```

アプリ利用者は、結果が最新なのか、どのbatchの結果なのかを確認できます。

## 同期実行と非同期実行

アプリからDuckDB処理を呼ぶときは、同期実行と非同期実行を分けて考えます。

同期実行が向く場面:

- 小さい品質チェックを即時確認する
- 管理者が手動で実行し、完了まで待てる
- 実行時間が短く、ロックや負荷が小さい

非同期実行が向く場面:

- 入力ファイルが大きい
- Parquet出力まで行う
- 外部DBやS3を読む
- 実行に数十秒以上かかる
- 失敗時の再試行やログ確認が必要

非同期実行にする場合、APIはすぐに結果を返すのではなく、ジョブIDを返す設計が自然です。

```json
{
  "jobId": "quality_check_2026_05_10_090000",
  "status": "queued"
}
```

このチュートリアルではジョブ管理までは実装しません。しかし、DuckDB処理をアプリに組み込む時は、処理時間とユーザー体験を考える必要があります。

## JSON contractのバージョン管理

一度アプリがJSONに依存すると、そのJSONは契約になります。

変更しやすいもの:

- 新しいフィールドを追加する
- `checks` に新しいチェック名を追加する
- `failureReasons` に新しい理由を追加する

壊れやすい変更:

- 既存フィールド名を変える
- 数値を文字列に変える
- `checks` の構造を配列からオブジェクトへ変える、または逆
- `ok` の意味を変える
- exit codeの意味を変える

実務では、必要なら `contractVersion` を入れます。

```json
{
  "contractVersion": 1,
  "ok": true,
  "totalErrors": 11,
  "checks": {}
}
```

このチュートリアルのCLIは小さく保っていますが、アプリ連携が増えるほど、JSON contractの互換性が重要になります。

## アプリ組み込みレビューの観点

Node.jsやWeb APIからDuckDBを使う設計をレビューするときは、次を確認します。

- Webリクエストごとに重い処理を実行していないか
- DuckDBファイルへ同時書き込みしない設計か
- JSON契約のフィールド名が安定しているか
- exit codeを呼び出し側が解釈しているか
- ユーザー入力から任意SQLを作っていないか
- 生成済み結果のbatchや時刻を返しているか
- SQL本体とアプリ表示ロジックが分離しているか

アプリ組み込みで重要なのは、DuckDBを隠すことです。アプリ利用者やフロントエンドは、DuckDB内部のraw/staging/martを知る必要はありません。安定した契約だけを見ればよい状態にします。

## よくあるつまずき

アプリから直接すべてのSQLを組み立てると、SQLインジェクションや保守性の問題が出ます。SQLはファイルに置き、アプリはパラメータや契約だけを扱う設計にします。

DuckDBをWebアプリの状態管理に使うと、同時書き込みや運用で苦しくなります。アプリDBはPostgreSQLなどに任せ、DuckDBは分析・検証に使います。

JSON出力に人間向け文言だけを入れると、アプリが判断できません。`ok`、`totalErrors`、`checks` のような構造化フィールドを用意します。

exit codeを設計しないと、バッチが成功・失敗を判断できません。JSONとexit codeの両方を契約として扱います。
